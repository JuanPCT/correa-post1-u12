# ADR-001: Integración mínima de patrones y límites del módulo

- Estado: Aceptada antes de implementar
- Fecha: 2026-11-20
- Contexto: solicitud de reembolso con categorías de gasto, validaciones ordenadas y tres interesados en cambios de estado.

## Problema

Las reglas de soporte documental, monto y duplicidad deben detener el flujo en el primer error. Cada categoría tiene una fórmula distinta. Empleado y auditoría reciben todos los cambios; contabilidad solo necesita solicitudes aprobadas. Debe poderse agregar una categoría o una etapa sin editar reglas existentes. El alcance actual es una aplicación UFPS pequeña con un equipo, una base H2 para la práctica y ningún cambio de motor planeado.

## Decisión

1. **Chain of Responsibility** para validar documentos, monto y luego duplicidad. Las reglas baratas corren antes de consultar persistencia.
2. **Strategy** para calcular el valor por categoría; un mapa construido desde estrategias Spring elimina un switch central.
3. **Observer** para difundir cada transición. Los observadores deciden si reaccionan; contabilidad filtra por estado aprobado. Los adaptadores de esta práctica registran eventos y no envían comunicaciones externas.
4. **Monolito por paquetes con puertos pequeños.** El procesamiento depende del contrato de repositorio en dominio y de notificaciones conocidas. Persistencia JPA y HTTP son adaptadores. ArchUnit protege las direcciones. No se añade bus distribuido, microservicios ni CQRS.

## Alternativas consideradas y descartadas

- **`ApplicationEventPublisher` de Spring:** útil con consumidores asíncronos o desacoplados por tiempo; tres listeners síncronos conocidos no justifican otra semántica de transacción, reintentos y depuración.
- **Decorator para capas opcionales de reembolso:** no se conoce un orden de composición de seguros, descuentos o impuestos. No se anticipa una plataforma de extensiones.
- **Repositorio JPA directo desde procesamiento:** menos tipos al inicio, pero mezcla regla con proveedor de datos y hace más difícil probar el flujo sin H2. El puerto definido por el dominio cuesta una interfaz y no justifica invertir toda la aplicación en capas hexagonales complejas.
- **Microservicios:** no hay equipos ni despliegues independientes que paguen red, consistencia eventual y operación duplicada.

## Consecuencias y revisión

La composición Spring resuelve estrategias y observadores desde el paquete; JPA/H2 permite integrar el flujo. Se conservan tests unitarios y un test SpringBootTest. Si el bus externo se vuelve requisito, se reabre ADR para outbox, idempotencia y política de reintentos. Si el equipo o los despliegues se separan, se revisan límites antes de extraer servicios.
